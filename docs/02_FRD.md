> **전체 제품 기준선**을 빠짐없이 기록하며, 이번 해커톤의 **실행 대상은 `09_RELEASE_SCOPE.md`**로 제한한다. 역할·권한은 `04_POLICY_RBAC.md`, 영속성은 `05_DATA_MODEL.md`가 기준.

> 2026-10-30 사용자 확정: React/Vite/Tailwind와 FastAPI, DB MariaDB를 사용한다. chatbot도 공통 사용자·로그인 세션·학적 원장을 사용하며 services/api 중심으로 통합한다. mvp는 사전 프로토타입으로 격리하고 최종 시연·제출·소스 복사에 사용하지 않는다. 최종 프런트는 apps/web에서 신규 작성한다. 아래 수용 조건은 요구사항이며 실제 구현 완료를 뜻하지 않는다.

## 0. 표준 정의
- 필수 필드: `ID`, 사용자, 트리거, 정상 결과, 예외, 권한, 연결 데이터, 수용 조건, 범위.
- 표의 기본 범위: `BASELINE`은 장기 제품의 기본 탑재 요구(해커톤 완료 아님); `INNOVATION`은 신규 차별화 요구.
- 기능의 완료 정의: UI 행동 → 인증된 서버 처리 → 권한 확인 → DB 기록 → 새로고침 후 재조회 → 오류/빈 상태 → 테스트 증거.
- 공통 예외: 비로그인 401, 권한 없음 403, 입력오류 400, 자료 없음 404, 상태 충돌 409, 과다 요청 429, 서버 오류 5xx. 클라이언트는 민감한 내부 정보를 표시하지 않는다.

## 2. 상세 명세 — 구현자가 반드시 따라야 할 계약

### FR-AUTH-001 — 인증·세션 [공통 선행]
- 입력: 이메일, 비밀번호(시연 전용 별도 계정); 출력: 서버가 검증한 사용자 ID·부여된 역할·허용 영역.
- 성공: 로그인 후 역할별 홈으로 이동; 새로고침해도 유효 세션이면 유지; 로그아웃 시 보호 페이지와 서버 API 접근 차단.
- 예외: 틀린 계정은 일반 오류; 비활성 계정 차단; 만료 세션은 재로그인 안내.
- 금지: 프런트에서 role, 학과, 학년 값을 보내고 서버가 그대로 신뢰하기; 로컬에 평문 비밀번호 보관.
- AC: (1) 비로그인 직접 URL 접근 차단 (2) 교차 계정 데이터 접근 차단 (3) 로그아웃 후 토큰 재사용 차단 (4) 에러에 키 유출 없음.

### FR-NOT-001 — 공식 공지 등록/수정/삭제
- 역할: 대학 전체 공지는 교내 권한자, 학과 공지는 해당 학과 승인된 조교·교수·담당자, 수업 공지는 담당 교수.
- 필수 입력: 제목(1~120자), 내용(1~10000자), 카테고리, 대상 scope, 게시/마감; 선택: 첨부파일, 중요도, 확인요청.
- 상태: `draft → published → archived`; `published` 자료 수정 시 `revision++`; 삭제는 소프트 삭제/감사 기록 우선.
- 대상 선택: `all`, `department`, `department_year`, `course_offering`, `individual` 중 서버가 허용한 범위만.
- 성공: 공식 원본 등록 → 대상 공지 목록 표시 → 자동 배포 이벤트 1회 → 수정 시 같은 ID 상세에 최신 내용 반영.
- 예외: 권한 없는 학과 선택 403; 게시 범위 누락 400; 동일 제출 중복 방지; 첨부 실패 시 공지 게시를 무조건 성공으로 표시하지 않음.
- AC: 정상 CRUD와 새로고침; 타 학과 비노출; 삭제/수정 뒤 기존 채팅 카드로 열었을 때 정확한 상태; 정정 이력 추적.

### FR-NOT-002 — 대상 채널 공식 카드 자동 배포
- 트리거: `published` 최초 발행, 재발행 알림이 명시적으로 필요한 개정.
- 매핑: 학과 대상→해당 학과 기본 채팅; 학과+학년→해당 학년 기본 채팅; 특정 수업→해당 수업 공지/수업 채팅(활성 시); 학교 전체→개인 알림 피드(전체 학과 채팅에 무차별 복사 금지).
- 실행: 서버 트랜잭션으로 원본 저장 후 배포 이벤트(outbox) 기록; 워커가 `notice_id + channel_id + revision + event_type`으로 중복 방지.
- 카드 내용: 공식 배지, 제목, 공지 유형, 해당 대상, 작성자 역할, 원본 URL, 새 버전 여부; **원문 전체 복사 금지**.
- 수정: 카드는 동일 원본 최신판으로 이동; 중요 수정은 별도 수정 안내 1회만.
- 실패: 자동 배포 실패해도 원본 공지가 사라지지 않아야 함. 재시도/실패 기록; 무한 재전송 금지.
- AC: 조교가 학과/학년 공지 등록 → 수강·소속 대상 학생만 채팅 카드 확인 → 원본 수정시 카드 상세 최신판 → 중복 발송 0.

### FR-DEPT-001~005 — 학과 채팅 / 자유 채널
- 기본 채널: 학과 전체, 학과×학년은 조직 정보 생성 시 자동 프로비저닝. 중복 unique key 제약.
- 참여: 서버가 확인한 현재 승인 소속·학년·역할이 대상 범위와 일치해야 조회/전송. P0 계약의 `academic_memberships` 유효 active 기록이 권한 입력이며 `profiles.department_id/academic_year`는 읽기 projection이다. 역할/전과/학년 변경 시 이전 소속 접근권 회수(이력 접근 범위는 04 정책).
- 자유 채널: 학과 구성원이 제목(2~60자), 설명, 가시성(`department_open`/`approval_required`)을 입력해 생성; 관리자는 운영정책 위반 시 조치.
- 공식 채널: 승인된 운영자가 생성/승인; 일반 학생은 `official=true` 설정 불가능.
- 메시지: 텍스트(1~2000자), 작성자·시각·채널·첨부 메타, 소프트 삭제, 정렬/페이지네이션, 실시간 신규 메시지. 재전송 시 클라이언트 idempotency key.
- AC: 학과 A 학생이 B 채널 접근 거부, 다른 학년 채널 접근 거부; 메시지 전송 후 다른 학생에게 실시간 반영; 재접속 뒤 DB 이력 유지; 탈퇴/권한 변경 시 즉시 차단.

### FR-COM-001~003 — 익명 자유 소통
- 로그인은 필수지만 작성 시 표시 이름은 `익명` 또는 대화 내 익명 번호. **익명 게시물 응답에 원 작성자 UID/실명/학과 등 신원 역추적 가능한 값 제공 금지**.
- 필수 입력: 제목(2~120자), 본문(1~5000자); 상태 `active/hidden/deleted`; 수정·삭제는 원 작성자만(서버 내부에서 매핑).
- 댓글/좋아요/북마크는 서버가 중복/소유권 검증, 누구나 신고 가능(본인 신고 처리 규칙 별도).
- 운영자에 한해 감사 목적 신원 연결 가능, 평소 서비스 운영 UI에는 신원 노출 최소화.
- AC: 사용자 A 글 작성→수정→삭제→재조회, 사용자 B는 A 신원을 알 수 없고 수정 불가; 신고·차단 작동; HTML 스크립트 주입 무력화.

### FR-COM-004~005 — 실명 팀원 모집
- 입력: 제목(2~120), 설명(1~5000), 분야/태그, 목표 인원(모집자 포함 총 정원, 2~20 기본값), 현재 모집 역할, 모집 마감, 관련 공모전(선택).
- 신원: 작성자는 공개 실명 활동 프로필만 표시. 실제 학교 인증 여부를 인증 완료처럼 표현하지 않음.
- 상태: `open/closed/cancelled`; 참가 지원 `pending/accepted/rejected/withdrawn`.
- 동시성: `accepted_count`는 모집자를 제외한 승인 지원자 수다. FastAPI 서비스 트랜잭션에서 변경 후 `1 + accepted_count ≤ capacity`를 보장하고 중복 지원·중복 승인을 막는다. 정원 수정도 같은 모집 행 잠금에 참여한다. 이는 모집자 포함 총 정원의 계약이며 실제 서버 구현 증거는 아니다.
- AC: 학생 A 모집글 CRUD, 학생 B 지원, A 승인, 인원 초과 동시 승인 실패, A 자신의 지원 불가, 모집 종료 후 지원 불가, 서로 다른 학과 참여 가능.

### FR-OPP-001~004 — 기회 목록·외부 지원 안내
- 공고: 카테고리(장학금/근로/취업/공모전/행사), 주최/게시자, 대상(학교·학과·학년), 접수기간, 지원 조건 원문, 외부 제출처·방법, 지정 파일/원본 링크.
- 외부 장학금 기본 유형: `external_document_submission` — 공식 지정 양식 다운로드→기관 지정 방식으로 직접 제출. 내부 `submit_application()` 같은 성공 처리 금지.
- 학생 관리: 공고 저장/취소, 개인 체크리스트 항목 CRUD, 마감일, 상태 `interested/preparing/self_reported_submitted/closed`.
- 외부 기관 제출 성공 여부는 자동 검증 불가. 상태명은 '사용자가 제출했다고 기록함' 의미로 유지.
- AC: 공고 원본·양식 접근, 개인 준비 항목 CRUD·새로고침, 다른 학생 상태 조회 불가, 마감 이후 신청 안내 최신 상태, 파일/링크 없으면 없다고 표시.

### FR-COURSE-001~004 — 내 강의실 기본
- 학기별 개설 분반(`course_offering`)이 강의실의 소유 단위. 관리자/교수 배정과 수강 등록은 서버가 승인.
- 학생은 자신이 등록된 강의실만 접근; 시간표에 연동; 교수는 담당 분반에 공지·자료(PDF/PPT/ZIP 등 안전 허용 형식)·과제를 게시.
- 과제: `draft/published/closed`, 제출 `submitted/resubmitted`, 평가·피드백 별도 권한. 첨부 접근은 수강생/담당자에 한정.
- AC: 교수 자료 등록→수강생 조회/다운로드→외부 학생 403, 교수 수정/삭제 반영, 파일 경로 추측으로 접근 불가, 과제 제출 시간은 서버 시각 기준.

### FR-COURSE-005 — 수업 채팅 + 질문 전용함
- 수업 채팅은 학생 간 소통, 질문 전용함은 교수가 확인하기 위한 별도 리소스.
- 질문 입력: 텍스트(1~2000), 공개/교수만 보기(기본값: 공개는 팀 확인 필요), 상태 `open/answered/resolved`.
- 교수만 공식 답변/질문 해결 표시, 작성자는 자신의 질문을 수정/철회 가능(답변 이후 변경 정책 안전한 기록형).
- AC: 교수 질문 목록 정렬, 학생 질문 생성·조회, 수강생 외 403, 실시간 수업 종료 후에도 보존 여부는 보존 정책 기준.

### FR-COURSE-006~007 — 실시간 화면 공유 및 원본 자료
- 교수는 강의실 세션을 시작하고 브라우저에서 직접 창/화면을 선택한다. 별도 권한 없는 자동 화면 캡처 금지.
- **학생은 보기만**. 참여자가 공유 권한을 가로챌 수 없어야 함. 화면 확대/전체화면 및 기본 음소거, 끊김/재연결 안내.
- PPT/PDF는 교수 업로드 파일이 있다면 별도 뷰어로 고화질 확대; VS Code 등 프로그램 실습은 화면 공유 영상으로 전달.
- 기술 옵션: WebRTC+SFU(LiveKit 등) 또는 신뢰할 수 있는 호스팅 서비스. 동시 30~40명 목표는 설계 가정이며 실측 전 보장 금지.
- 예외: 브라우저 미지원, 권한 거절, 공유 중지, 네트워크 지연, 토큰 만료, 세션 정리.
- AC: 교수 PC 1, 학생 2 이상이 각 계정으로 같은 수업 세션에 접속→수업 화면 재생→공유 중지 시 종료 표시; 수강생 아닌 계정 접근 거부. 녹화·음성 저장 **기본 비활성**.

### FR-ATT-001~002 — 출결 기본
- 교수가 수업 출석 세션을 시작/종료; 학생 체크인(코드/QR은 구현 옵션) 후 교수 최종 확인·정정, 사유/이력 관리.
- 화면 코드만으로 실제 현장 재실을 인증했다고 주장하지 않음. 교수가 권한 있는 최종 변경.
- 지각·출석·결석 판정 규칙은 학사 정책 승인 전 임의 확정 금지. 해커톤에서는 `present/late/absent`를 시연용 표시만.
- AC: 임의 학생이 타 학생 출결 수정 불가; 교수 담당 분반만 수정, 모든 수정 기록 감사.

### FR-AI-001~003 — 맞춤형 AI
- 입력: 사용자가 접근할 수 있는 공지·과제·시간표·기회·준비상태·관심 분야 중 최소 정보만 서버에서 취합.
- 서버에서 정해진 규칙으로 기간·마감·대상을 계산하고, AI는 **설명과 우선순위 이유**를 구조화된 JSON으로 생성.
- 출력 스키마: `{summary: string, actions: [{title: string, reason: string, source_type: string, source_id: string}], cautions: string[]}`. URL이나 권한을 모델 출력만 믿고 사용하지 않음.
- 근거 원본 링크/자료 없는 정보는 확정 사실처럼 표시하지 않음. JSON 검증 실패 시 규칙 기반 결과 또는 오류 안내.
- 한도: 사용자 인증, 글 길이 제한, 분당·일당 제한, 제한시간, 실패 시 대체 화면. 비용/모델 변경은 서버 설정.
- AC: 사용자 A/B 서로 다른 데이터에서 개인화 결과가 달라짐; 모델 지연·실패해도 홈 이용 가능; 프롬프트 주입된 공지 텍스트가 시스템 지시를 바꾸지 못함; 응답 스키마 검증.

## 3. 전 제품 BASELINE 기능의 상세화 규칙
`FR-ACA-*`, `FR-CAMP-*`, `FR-OPP-006`, `FR-COM-006~007` 등 P2 범위 기능도 **제품 요구사항으로 유지**한다. 단 위 상세 명세에 없는 기간 계산/학적·성적·도서관/증명서 발급 등은 운영정책과 개인정보/학교 권한이 미확정이므로 AI가 임의 구현하지 않는다. 구현 시작 전 같은 템플릿(입력, 권한, 상태기계, 오류, 수용기준)을 별도 섹션으로 확장한다.
