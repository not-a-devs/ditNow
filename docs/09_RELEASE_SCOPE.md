# 전체 92개 1차 구현과 해커톤 우선순위

## 1. 전체 범위와 완료 게이트
2026-10-30 사용자 결정 DEC-018: 전체 92개 기능을 1차 구현 범위로 추적한다. P0 완료로 개발을 종료하지 않는다. 전체 자동 검사→사용자 직접 검사→보완·재기획을 반복한다. 사전 mvp 코드는 최종 앱/제출에서 제외하고 apps/web에 새로 작성한다.
- **PRODUCT BASELINE**: 사용자가 확정한 목표대로 기존 대학 앱/웹의 주요 학사·LMS·출결·지원·행정·도서관 기능을 전체 제품 설계에 포함.
- **HACKATHON BUILD**: 27시간 경진대회에서 실제 검증 가능한 작동 코드를 단계적으로 완성. 장기 필수 기능이라도 개발 우선순위는 P1/P2일 수 있다.

## 2. P0 — 심사 우선 수직 흐름(제안, 팀 승인 필요)
### P0-A 기반
1. 기존 사용자 적격성 해결 확인을 보존하고, 신규 앱+배포, 환경변수/DB 마이그레이션/기본 디자인 시스템
2. 공통 로그인/FastAPI 권한/MariaDB 최소 권한, 학과·학년 2개/학생 3명/조교 1명 시드
3. 390/1280 레이아웃, 오류/빈/로딩/재시도

### P0-B 핵심 3개 CRUD (README 1~3번 후보)
1. **학생 익명 자유게시판 글 CRUD** — 익명 신원 노출 금지
2. **학생 실명 팀 모집글 CRUD** — 정원/모집상태, 추후 지원 연결
3. **학생의 기회 저장·개인 준비상태 CRUD** — 외부 지원서 기본 규칙

### P0-C 하나의 서비스 증명
4. **조교의 공식 학과 공지 발행→해당 학년 채팅의 공식 카드 자동 배포→학생 열람** (최소 1개 실제 연결)
5. **학과 전체/학년별 채팅 메시지 DB 영속 + 실시간 수신** (최소 A/B 2명)
6. **개인 DB 데이터 기반 AI 액션/공지 브리핑** (실패 시 홈 가용)
7. 보안/동시성/접근성/성능/README/시연 증거

> P0는 많아 보일 수 있다. 개발 진척이 부족하면 핵심 3 CRUD와 인증·권한·공지 연결 1건, AI 실패 안전장치를 먼저 보호한다. 라이브 스트리밍·행정 시스템을 P0로 과하게 확장하지 않는다.

## 3. P1 — 공통 의존성 충족 시 병렬 착수, P0 출시 품질 보호
- 내 강의실 목록·교수 강의 자료 업로드/학생 열람
- 교내 공지/기회 센터의 관리자 상세 CRUD 및 원본 다운로드
- 실명 팀원 지원·승인/인원 동시성 처리
- 학과 자유채널 개설·초대/관리
- 학생 질문 전용함, 과제 등록/제출
- **실시간 교수 화면 공유 PoC → 사용자 시나리오까지 검증된 경우에만 시연 기능으로 승격**

## 4. P2 — 전체 1차 구현 대상, 정책별 안전한 시연과 운영 차단 분리
- 수강신청/정정/학적·성적·증명서, 정교한 출결·학사 규칙
- 도서관 운영·예약/시설 관리, 학생 상담/민원, 장학금 내부 승인
- 실시간 스트리밍 다수 동시접속 본격 운영, 강의 녹화 정책 검토
- 스터디·동아리 고도화/팀 활동 이력·포트폴리오
- 정교한 AI 추천·관심사 분석·통합 검색/앱 푸시

## 5. 중단·강등 기준
- 인증+DB+CRUD 우선 자원을 확보한다. 공통 파일과 충돌하지 않는 P1/P2 구현은 병렬 진행하며 미검증 고급 기능을 출시 완료로 표시하지 않는다.
- P0 완료 전 새 기능 홍보/겉모습 기능 위주 개발 금지.
- 출시 직전 기능 새로 추가하지 않음. 미검증 기능은 숨기거나 `준비 중`(실제 클릭 시 의미 있게 안내) 처리.
- 팀은 현재 작업 기준으로 P1을 조기 승격시킬 수 있으나 `DECISION_LOG`에 승인·근거 기록 필수.

## 6. 대표 4분 시연 흐름 (제안)
1. 문제(단톡 공지 중계/기회 찾기/학과간 협업) 30초.
2. 학생 계정으로 익명 게시글 및 실명 모집 CRUD와 기회 준비 상태 90초.
3. 조교 계정으로 학과 공지 등록→학생 학년 채팅 자동 카드 확인 70초.
4. 학생 홈·AI 개인화 요약과 권한/DB 영속성 확인 50초.
- 라이브 화면 공유는 준비·검증된 경우 짧게 교체 시연하고 미검증 상태에서는 과장하지 않는다.
